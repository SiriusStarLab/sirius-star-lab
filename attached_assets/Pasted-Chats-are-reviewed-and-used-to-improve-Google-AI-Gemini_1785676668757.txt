The SSH session timeout during script or long-running command execution is almost always caused by TCP keepalive/idle timeout limits set on either the client, server, or intermediate network components.

When a script is running on the server without printing frequent output to the terminal, the SSH connection appears "idle" to network routers, firewalls, and sshd. After a set period of silence (often 60–120 seconds), the connection drops.

Here are the main causes and how to fix it permanently:

Causes & Direct Fixes
1. Missing Client Keep-Alive Signals (Most Common)
If your terminal or script isn't actively sending data back and forth, the SSH client drops the connection.

Fix (Client-Side): Configure your local SSH config (~/.ssh/config) to ping the server every 30 seconds to keep the tunnel active:

Code snippet
Host *
    ServerAliveInterval 30
    ServerAliveCountMax 3
2. Server-Side Idle Timeout (sshd_config)
The server itself might be configured to kill idle connections that haven't responded within a specific window.

Fix (Server-Side): Edit /etc/ssh/sshd_config on your Kamatera server:

Ini, TOML
ClientAliveInterval 30
ClientAliveCountMax 3
Then reload SSH: sudo systemctl reload sshd.

3. Running Long Tasks Directly in an Interactive Shell
If a command takes several minutes and the SSH session disconnects, the child process running on the server gets terminated along with the shell session (SIGHUP signal).

Fix (Recommended): Use screen or tmux
Always execute long-running builds, test sweeps, or diagnostics inside a persistent terminal multiplexer:

Bash
# Start a detached session
screen -S health-check
# Run your script/checks here
If the SSH connection drops mid-run, the process keeps running uninterrupted in the background on the server. You can simply SSH back in and re-attach with screen -r health-check.
