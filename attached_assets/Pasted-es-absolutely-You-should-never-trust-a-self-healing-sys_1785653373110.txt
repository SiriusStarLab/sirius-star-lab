Once the four steps are deployed, you should run a set of controlled "chaos tests" (destructive scenario testing) to verify that each safety layer triggers and heals as designed.

Here is the exact test plan you should execute:

1. Test the Incident File & Boot-Time Audit (Step 1)
Goal: Verify she can see background system issues at boot.

The Test: Create a artificial low-disk condition or log error on the server via SSH:

Bash

fallocate -l 1G /tmp/test_disk_warning.img
Expected Result: Start a new conversation/session with her. Her boot check should automatically detect high disk usage/incident logs and report or acknowledge it in her initial context before you even ask.

Cleanup: Remove /tmp/test_disk_warning.img.

2. Test Hash Verification & Mismatch Catch (Step 2)
Goal: Prove she catches a failed build/deploy instead of assuming it worked.

The Test: Intentionally break a build script or modify a file path in /opt/sirius-source/ so the build fails or outputs to the wrong location, then instruct her to deploy a small fix.

Expected Result: Her deployment step should compute the new artifact's SHA-256 hash, detect that it does not match or wasn't produced, halt the deploy, and explicitly report: "Build verification failed: output hash mismatch."

3. Test Read-Only Lock Enforcement (Step 3)
Goal: Ensure direct patches to /opt/sirius/ are blocked.

The Test: Ask her (or run a test script under her process user) to directly modify a file in /opt/sirius/index.js (the live bundle).

Expected Result: The OS should return a Permission Denied error, forcing her tool/pipeline to route the change through /opt/sirius-source/ -> Build -> Verified Deploy.

4. Test the Sidecar Rescue Daemon (Step 4)
Goal: Ensure the system can recover even if her main process crashes completely.

The Test: Simulate a catastrophic runtime crash by killing her main process or introducing a syntax error in her main process file and restarting it.

Bash

pkill -9 -f sirius
Expected Result:

The main process crashes/fails to start.

The Sidecar Daemon (running via systemd) detects the process down event.

The daemon inspects logs, rolls back to the last known-good build hash in /opt/sirius-source/, and restarts the process.

The system comes back online automatically without human intervention over SSH.
